# GTD 入門

GTD (Getting Things Done) は、David Allen が提唱した仕事の進め方です。前提はひとつだけで、**頭は物事を記憶しておくための器官ではなく、考えるための器官である**、というものです。

「あの件のメールを返さなきゃ」と1日に何度も思い出すのは、頭がそれを記憶しようと努力しているからです。この努力は考える力を削ります。そこで、気になることを **すべて頭の外に出し、信頼できる仕組みに預ける**。頭が「もうここにあるから覚えていなくていい」と納得したとき、初めて目の前のことに集中できる。これが GTD の狙いです。

やることは5つの段階に分かれます。順番に意味があるので、飛ばさずに読んでください。

## 1. Capture — とにかく外に出す {#capture}

気になっていることを、判断せずに、片っ端から書き出します。仕事も私用も、大きい小さいも区別しません。この段階で「これは重要か」「どうやるか」を考えてはいけません。**考えると手が止まり、書き出しが終わらなくなります。**

最初の1回は、頭の中を空にするためにまとまった時間を取ります。1〜2時間かけて、思いつく限り全部出す。「タイヤを交換する」「誕生日プレゼント」「引き継ぎ資料のこと」——単語でも構いません。後で自分が読んで思い出せれば十分です。

以降は、思いついた瞬間に放り込むだけです。**ここに入れた項目は未処理** であり、まだ何も約束していません。

## 2. Clarify — それは何かを決める {#clarify}

**これは日常的に、できれば毎日、短い時間で繰り返すものです。** Clarify を溜めると、頭は「あそこを見ても何があるか分からない」と判断して、また自分で覚え始めます。

集めた項目を1件ずつ取り上げ、次の問いに答えます。**必ず1件ずつ、上から順に。** 一覧を眺めて「やりやすいものから」と選び始めると、難しい項目だけが永久に残ります。

最初の問いは **「これは行動を要するか?」** です。

行動を要さないなら、行き先は3つです。

- **捨てる** — もう気にならない、必要ない。
- **Reference にする** — 行動ではないが、取っておきたい情報。いつか読む記事、参考になる手順、連絡先。
- **Someday/Maybe** — 今はやらないが、可能性としては残しておきたい。

行動を要するなら、次の問いは **「望む結果は1つの行動で終わるか?」** です。

2つ以上の行動が要るなら、それは **Project** です (下記)。そして、その Project について **次に取る1つの行動（Next Action）** を決めます。

1つの行動で終わるなら、その行動を **2分以内にできるか** を見ます。

- **2分以内にできる** — その場でやってしまいます。記録して管理するほうが高くつきます。
- **自分がやるべきでない** — 人に頼み、**誰に何を頼んだかを記録** します。これが「Waiting For」です。頼んだ時点で自分の手を離れますが、追いかける責任は残ります。
- **特定の日にしかできない** — Scheduled にして日付を持たせます。今日から見えている必要はありません。
- **それ以外** — Next Actions のリストに入れます。

ここで最も大事なのは、**Next Action は物理的に実行できる単一の動作として書く** ことです。「〇〇の件」「確定申告」はどちらも行動ではありません。「税理士の田中さんに電話して、必要書類を聞く」が行動です。曖昧に書かれた項目はリストの中で腐り、見るたびに考え直す羽目になります。**Clarify の段階でここを面倒がると、後の全部が機能しなくなります。**

## 3. Organize — 行き先ごとに置く {#organize}

Clarify した結果を、種類ごとに別の場所に置きます。同じリストに混ぜないことが肝心です。

### Project {#project}

GTD でいう Project とは、**1年以内に完了でき、2つ以上の行動を要する、望ましい結果** のことです。会社で言う「Project」より遥かに小さく、「自転車を修理する」も立派な Project です。

Project には **Outcome** を1文で書きます。「オフィス移転」ではなく「新オフィスに移転完了し、業務が再開している」。Outcome が書けない Project は、たいてい自分でも何をしたいのか分かっていません。そして Outcome が定まると、Next Action が驚くほど決めやすくなります。

Project のリスト自体は、実行するためのものではありません。**見落としがないかを確認するための棚卸しリスト** です。実行するのは常に Next Action です。

<!--feature:contexts-->
### Context {#context}

その行動を実行するのに必要な道具や場所です。`@電話` `@自宅` `@買い物` `@メール`。

これは分類の趣味ではなく、実用のためです。電車の中で開いたときに、家でしかできない行動が並んでいても邪魔にしかなりません。**今いる場所でできることだけが見える** ようにするのが Context の役割です。

<!--feature:areas-->
### Area of Responsibility {#area}

「経理」「健康」「チームの採用」のような、**完了することのない、維持し続ける領域** です。Project が終わっても、Area of Responsibility は終わりません。

これは行動のリストではなく、点検のための見出しです。Weekly Review で「健康について、今なにも動いていないが、それでいいか?」と自問するために使います。

## 4. Reflect — 仕組みを信頼できる状態に保つ {#review}

**GTD で唯一、必ず守らなければならない習慣がこれです。** 週に1度、1時間ほどかけてリスト全体を見直します。

なぜ必要か。頭が仕組みを信頼するのは、**中身が最新だと知っているとき** だけです。2週間見ていないリストを頭は信用しません。信用しない頭は、また自分で覚え始めます。そうなると、書き出した意味がなくなります。

この段階ですること。

- 残っている未処理を空にする (週の途中で Clarify しきれなかった分を、ここで取り返す)
- 頭の中をもう一度空にする
- Next Actions を最初から読み、終わったもの・意味を失ったものを片付ける
- 先週を振り返り、これからの予定を確認する
- Waiting For を見直し、返事が来ていないものを催促する
- **Project を1つずつ見て、Next Action があるか確かめる**
- **Someday/Maybe を見て、今やることに昇格するものがないか確かめる**

最後の2つが最も重要です。**Next Action が1つもない Project は、止まっていることに誰も気づかないまま止まります。** そして Someday/Maybe を見直さない仕組みでは、そこはただのゴミ箱になります。

## 5. Engage — 何をやるか決める {#engage}

その瞬間に何をするかは、4つの基準で絞ります。**Context** (今どこにいて何が使えるか)、**使える時間**、**残っている気力**、そして最後に **重要度**。

重要度が最後に来るのは意外に見えますが、順番として自然です。5分しかないとき、その5分で最も重要なことをやるのではなく、5分でできることの中で最も重要なことをやるしかありません。

## よくあるつまずき {#pitfalls}

**Next Actions に行動でないものが混ざる。** 「〇〇の件」が並び始めたら危険信号です。リストを見るたびに「で、何をするんだっけ」と考え直すことになり、だんだんリストを開かなくなります。

**未処理の箱を保管庫にする。** 入れっぱなしで Clarify をしないと、そこは「見たくないものの山」になります。空にできない日があってもいいですが、週に1度は必ず空にします。

**Weekly Review をしない。** GTD が続かなかったという話のほとんどはこれです。他の全部を雑にやっても、Weekly Review だけは残してください。

**最初から完璧な分類を作ろうとする。** Context も Area of Responsibility も、使いながら必要になった分だけ増やせば十分です。使われない分類はただの手間です。
