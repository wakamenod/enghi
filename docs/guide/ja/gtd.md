# GTD 入門

GTD (Getting Things Done) は、David Allen が提唱した仕事の進め方です。前提はひとつだけで、**頭は物事を記憶しておくための器官ではなく、考えるための器官である**、というものです。

「あの件のメールを返さなきゃ」と1日に何度も思い出すのは、頭がそれを記憶しようと努力しているからです。この努力は考える力を削ります。そこで、気になることを**すべて頭の外に出し、信頼できる仕組みに預ける**。頭が「もうここにあるから覚えていなくていい」と納得したとき、初めて目の前のことに集中できる。これが GTD の狙いです。

やることは5つの段階に分かれます。順番に意味があるので、飛ばさずに読んでください。

## 1. 把握 — とにかく外に出す {#capture}

気になっていることを、判断せずに、片っ端から書き出します。仕事も私用も、大きい小さいも区別しません。この段階で「これは重要か」「どうやるか」を考えてはいけません。**考えると手が止まり、書き出しが終わらなくなります。**

最初の1回は、頭の中を空にするためにまとまった時間を取ります。1〜2時間かけて、思いつく限り全部出す。「タイヤを交換する」「誕生日プレゼント」「引き継ぎ資料のこと」——単語でも構いません。後で自分が読んで思い出せれば十分です。

以降は、思いついた瞬間に放り込むだけです。**ここに入れた項目は未処理**であり、まだ何も約束していません。

## 2. 見極め — それは何かを決める {#clarify}

集めた項目を1件ずつ取り上げ、次の問いに答えます。**必ず1件ずつ、上から順に。** 一覧を眺めて「やりやすいものから」と選び始めると、難しい項目だけが永久に残ります。

最初の問いは **「これは行動を要するか?」** です。

行動を要さないなら、行き先は3つです。

- **捨てる** — もう気にならない、必要ない。
- **資料にする** — 行動ではないが、取っておきたい情報。いつか読む記事、参考になる手順、連絡先。
- **いつかやる** — 今はやらないが、可能性としては残しておきたい。

行動を要するなら、次の問いは **「望む結果は1つの行動で終わるか?」** です。

2つ以上の行動が要るなら、それは**プロジェクト**です (下記)。そして、そのプロジェクトについて**次に取る1つの行動**を決めます。

1つの行動で終わるなら、その行動を **2分以内にできるか** を見ます。

- **2分以内にできる** — その場でやってしまいます。記録して管理するほうが高くつきます。
- **自分がやるべきでない** — 人に頼み、**誰に何を頼んだかを記録**します。これが「連絡待ち」です。頼んだ時点で自分の手を離れますが、追いかける責任は残ります。
- **特定の日にしかできない** — その日付に紐づけます。今日から見えている必要はありません。
- **それ以外** — 「次の行動」のリストに入れます。

ここで最も大事なのは、**「次の行動」は物理的に実行できる単一の動作として書く**ことです。「〇〇の件」「確定申告」はどちらも行動ではありません。「税理士の田中さんに電話して、必要書類を聞く」が行動です。曖昧に書かれた項目はリストの中で腐り、見るたびに考え直す羽目になります。**見極めの段階でここを面倒がると、後の全部が機能しなくなります。**

## 3. 整理 — 行き先ごとに置く {#organize}

見極めた結果を、種類ごとに別の場所に置きます。同じリストに混ぜないことが肝心です。

### プロジェクト {#project}

GTD でいうプロジェクトとは、**1年以内に完了でき、2つ以上の行動を要する、望ましい結果**のことです。会社で言う「プロジェクト」より遥かに小さく、「自転車を修理する」も立派なプロジェクトです。

プロジェクトには**完了状態**を1文で書きます。「オフィス移転」ではなく「新オフィスに移転完了し、業務が再開している」。完了状態が書けないプロジェクトは、たいてい自分でも何をしたいのか分かっていません。そして完了状態が定まると、次の行動が驚くほど決めやすくなります。

プロジェクトのリスト自体は、実行するためのものではありません。**見落としがないかを確認するための棚卸しリスト**です。実行するのは常に「次の行動」です。

### コンテキスト {#context}

その行動を実行するのに必要な道具や場所です。`@電話` `@自宅` `@買い物` `@メール`。

これは分類の趣味ではなく、実用のためです。電車の中で開いたときに、家でしかできない行動が並んでいても邪魔にしかなりません。**今いる場所でできることだけが見える**ようにするのがコンテキストの役割です。

### 責任範囲 (Areas of Responsibility) {#area}

「経理」「健康」「チームの採用」のような、**完了することのない、維持し続ける領域**です。プロジェクトが終わっても、責任範囲は終わりません。

これは行動のリストではなく、点検のための見出しです。週次の見直しで「健康について、今なにも動いていないが、それでいいか?」と自問するために使います。

## 4. 見直し — 仕組みを信頼できる状態に保つ {#review}

**GTD で唯一、必ず守らなければならない習慣がこれです。** 週に1度、1時間ほどかけてリスト全体を見直します。

なぜ必要か。頭が仕組みを信頼するのは、**中身が最新だと知っているとき**だけです。2週間見ていないリストを頭は信用しません。信用しない頭は、また自分で覚え始めます。そうなると、書き出した意味がなくなります。

見直しですること。

- 集めたものを空にする (未処理を全部見極める)
- 頭の中をもう一度空にする
- 「次の行動」を最初から読み、終わったもの・意味を失ったものを片付ける
- 先週を振り返り、これからの予定を確認する
- 連絡待ちを見直し、返事が来ていないものを催促する
- **プロジェクトを1つずつ見て、次の行動があるか確かめる**
- **「いつかやる」を見て、今やることに昇格するものがないか確かめる**

最後の2つが最も重要です。**次の行動が1つもないプロジェクトは、止まっていることに誰も気づかないまま止まります。** そして「いつかやる」を見直さない仕組みでは、そこはただのゴミ箱になります。

## 5. 実行 — 何をやるか決める {#engage}

その瞬間に何をするかは、4つの基準で絞ります。**コンテキスト** (今どこにいて何が使えるか)、**使える時間**、**残っている気力**、そして最後に**重要度**。

重要度が最後に来るのは意外に見えますが、順番として自然です。5分しかないとき、その5分で最も重要なことをやるのではなく、5分でできることの中で最も重要なことをやるしかありません。

## よくあるつまずき {#pitfalls}

**「次の行動」に行動でないものが混ざる。** 「〇〇の件」が並び始めたら危険信号です。リストを見るたびに「で、何をするんだっけ」と考え直すことになり、だんだんリストを開かなくなります。

**未処理の箱を保管庫にする。** 入れっぱなしで見極めをしないと、そこは「見たくないものの山」になります。空にできない日があってもいいですが、週に1度は必ず空にします。

**見直しをしない。** GTD が続かなかったという話のほとんどはこれです。他の全部を雑にやっても、週次の見直しだけは残してください。

**最初から完璧な分類を作ろうとする。** コンテキストも責任範囲も、使いながら必要になった分だけ増やせば十分です。使われない分類はただの手間です。
